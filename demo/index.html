    Demo¶

    The examples each show one concept. A demo is a whole application built with odf, closer to a real business, using most of ODF at once. It lives in demo/ and runs with docker compose up.

    Bakery¶

    demo/bakery is a bakery that bakes overnight, delivers to eight restaurants each morning, and runs its own café. It already uses a café POS, a business messenger, email and spreadsheets on a shared drive, and none of them talk to each other. Each tool runs as a simulated service of its own, with its own UI and API. An odf project connects them the ways real integrations do, and answers the questions that cross them: what to bake tomorrow, which contracts are losing money, and who to tell when a flour may contain sesame.

    cd demo/bakery
docker compose up --build

    Then open the bakery's UI at http://localhost:4747, the world console (the demo clock, scenarios and tours) at http://localhost:8000, and the tools next to it. A tour plays one of the bakery's flows end to end, from a restaurant's message or a supplier's invoice to the draft a person confirms, saying at each step what to look at, and moves on as the bakery's notifications arrive. The README explains why it's built this way, what to try, and the questions to ask in chat.

    What it shows¶

    In the bakery What ODF does Docs
    The POS and the messenger push webhooks; the mailbox is polled; the sheets are watched; a scheduler runs the bakery's day Each integration is a @Service or @Component, and each inbound item one @Function call, so it's logged and traced on its own Service, Function
    A restaurant's message, a supplier's invoice and a price rise each raise a notice in the UI Components publish notifications; every open tab shows those with a summary, and the Notifications view keeps them all UI
    A message becomes a draft order change, and an invoice runs a chain: prices, then margins, then a renegotiation draft @Subscribers react in the background, each reaction a call caused by the notification before it, so Show run shows the whole chain as one tree UI
    The topology shows who reacts to whom before anything happens Dotted links from each @Publisher to the @Subscribers its topics reach UI
    A manager sees the bakery; whoever runs it sees the wiring too Two views in config.toml: manager, shown first, with the data, the agents, the night run and closing the café, the draft actions and a manager's questions; system with everything else as well, each laid out on its own in layout.json UI
    The topology groups the nodes by area One @Layer per area (integrations, wholesale, cafe, production, purchasing, allergens, drafts), matching layout.json's bands, so the sidebar groups them as the canvas lays them out Layer
    The bakery's staff at their desks, an oven, a display case, an invoice and the delivery van on the canvas The bakery's own icons for every node, one desk for each agent, in a script loaded through [ui] icon-scripts, each node's saved in layout.json, on the built-in ink theme picked by [ui] theme UI
    Agents draft; people confirm @Agents with plain rules first and a local model for the rest, writing drafts that confirm-draft sends out Agent, Arguments
    Each restaurant's messages in one thread in the chat, both sides, with the draft answering them as a card to confirm, edit or reject Messages and Drafts declare a conversation() in one channel, and confirm-draft, edit-draft and reject-draft take Annotated[int, Record(Drafts)], so they're the card's actions, its reply filled in to change first Chat
    A restaurant writing again before its draft is confirmed, or a person asking in the thread to "make it 30", outdates the draft for a new one The order-desk agent drafts from the new message and those the open draft answered, or with the instruction; asked in a thread, the assistant has the thread as context Chat
    Messages and invoices as documents, deliveries on a map, prices and café sales over time, margins as a chart DocumentView, LocationView, grouped TimeseriesView, chart() Data views
    "What do we bake tomorrow?" and "Which restaurants are we losing money on?" The same agents and functions as MCP tools, and in the chat window on a local model MCP, Chat

    The bakery, the restaurants, the people and the data are all fictional.
